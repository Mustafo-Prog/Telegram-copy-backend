# Сервер мессенджера

Запуск: `npm install`, затем `npm run dev` или `npm start`. Переменные окружения перечислены в `.env.example`.

Проверки: `npm test`. HTTP- и Socket.IO-тесты используют базу в памяти и временные локальные серверы.

## Статусы аккаунтов

Поле `users.status` принимает `user`, `admin`, `superadmin`. Новые аккаунты получают `user`; отсутствие поля у старого аккаунта также означает `user`. `admin` обозначает Premium и само по себе не добавляет прав. `premiumExpiresAt` хранит конечную дату подписки в UTC, `premiumVersion` защищает от устаревших обновлений. Платёжная система пока не подключена.

`superadmin` может удалять любые сообщения в общем чате и выдавать Premium через Promote в профиле другого пользователя. Для начальной настройки владелец вручную задаёт своему документу в MongoDB Atlas `status: "superadmin"` и обновляет страницу. Значение `admin` означает только Premium. Автоматического назначения владельца и публичного API для выдачи `superadmin` нет.

`POST /api/users/:id/promote` доступен только суперадмину и всегда назначает `admin`; самоназначение и изменение другого суперадмина запрещены. Тело `{ durationDays }` задаёт целое число дней от 1 до 365 (по умолчанию 30). Сервер сам рассчитывает дату; произвольные `status` и `premiumExpiresAt` из запроса не назначаются. Повторная первоначальная выдача действующему Premium не меняет его дату. Для продления передаются `{ durationDays, renew: true, expectedExpiresAt, expectedVersion }` из текущего профиля: дни добавляются к оставшемуся сроку, а устаревшая или повторная операция получает `409 premium_changed`. Истёкшую подписку можно выдать заново от текущего времени.

При первом запуске обновления существующие `admin` без даты получают ровно 30 дней. Повторные запуски их срок не сдвигают. Периодическое обслуживание переводит истёкшие подписки в `user` и публикует события; API уже в момент дедлайна возвращает эффективный `user`, даже если фоновой обработке ещё предстоит выполнить запись. Аккаунты не удаляются. `superadmin` всегда бессрочен и исключён из этой обработки, в том числе если в его документе по ошибке указана дата.

Обычное редактирование профиля и вход не позволяют передать себе статус или срок. Права проверяются по текущему документу пользователя, а не по данным из клиента или роли внутри JWT. События `account:updated` и `user:updated` содержат `premiumExpiresAt` и `premiumVersion`; клиент игнорирует устаревшие версии и убирает значок Premium по таймеру даже без сети.

`GET /api/users/by-id/:id` возвращает публичный профиль вошедшему пользователю, в том числе для аккаунтов без @ника. Статусы аккаунта независимы от прав владельца и администраторов отдельной группы: ни Premium, ни `superadmin` не предоставляют доступ к чужим приватным перепискам или управление чужими группами.

## Избранное

- `POST /api/conversations/saved` возвращает `{ conversation }`: личное «Избранное» текущего пользователя. Повторный запрос открывает тот же чат.
- `POST /api/conversations/saved/messages/:messageId` возвращает `201 { conversation, message }` и сохраняет отдельную копию доступного сообщения, включая файл или голосовую запись. Удаление оригинала не удаляет сохранённую копию.
- Для заметок, загрузки истории, поиска, редактирования и удаления используются обычные `/api/conversations/:id/...` маршруты. `kind` такого чата — `saved`, `peer` — `null`. Чат и его файлы доступны только владельцу.
- `message.savedFrom` содержит имя исходного автора и время оригинала. Цитата из другого чата не переносится.

Для этой функции новые переменные окружения не нужны.

## Синхронизация

- `GET /api/messages/:id/readers` возвращает `{ messageId, readers }` для собственных сообщений в группе или общем чате. Читатели определяются по сохранённым курсорам прочтения; собственный просмотр исключается. Для приватной группы нужны членство и доступ к сообщению. В ответ попадают только публичные поля профиля текущих участников.
- `PUT /api/messages/:id/reactions` принимает `{ emoji, active }` для доступного сообщения. Поддерживаются `👍 ❤️ 😂 😮 😢 🔥 🎉 👎`; повторная установка того же состояния не создаёт дублей. Ответ и событие `message:reactions` содержат `messageId`, `scope`, `conversationId`, `reactions` (эмодзи, количество и ID пользователей), `reactionsVersion`. Клиент игнорирует версии старше уже полученной. Реакции возвращаются и в обычных DTO сообщений. Миграция существующих документов не требуется.

Закрепление возвращает только `{ conversation: { id, pinnedAt } }`. Клиент должен объединять эти поля с сохранённым чатом. Событие `chat:changed` с `reason: pin` содержит `conversationId` и `pinnedAt`.

Полные DTO диалогов содержат `lastMessageId`. Отправка текстом или `multipart/form-data` принимает необязательный `clientMessageId` (строка длиной 1–80 символов), который возвращается в сообщении и событии Socket.IO для сопоставления с локальным индикатором отправки. Это идентификатор интерфейса, а не гарантия повторной отправки без дублей.
